## Order, and why it is this order

1. **Task 1 (§D23, PG-107) first.** §D21's fallback for the 3.1% of messages the index cannot
   resolve by `Message-ID` reads the ledger's ROWID — which does not exist until the bridge is
   recorded. Doing §D21 first means shipping a «Rigenera» whose fallback is dead code.
2. **Task 2 (§D24 probe, PG-108) needs a person at the keyboard** and gates Task 3's SQL. Run it
   early so it is not the thing blocking the last batch.
3. **Task 3 (§D24) and Task 4 (§D22)** both touch `MembershipRule`; Task 3 lands first because
   Task 4's keyword arm calls the predicate Task 3 extracts.
4. **Task 5 (§D21)** last: it is the only task with a new UI surface, and it consumes Task 1's
   ledger.
5. **Task 6** is the contract-staleness sweep and the full suite.

## Risks, dependencies and HITL gates

- **HITL — Task 2's live probe.** A person has to be present. It reads a published copy, never
  Mail's live file, and reads schema plus addresses only. Do not let an unattended dispatch run it.
- **HITL — commit, push, merge.** As always in this repo: never on `main`, never force-pushed,
  `scripts/uitests.sh` green before the merge.
- **Dependency: Task 1 before Task 5.** §D21's ledger fallback is dead code otherwise.
- **Dependency: Task 2 before Task 3.** The SQL Task 3 ships is only as good as the schema Task 2
  confirms.
- **Risk: the shipped tray may already be empty on the real store** (finding F5). If Task 2 finds a
  different `recipients` shape, the tray has never worked outside the fixture and the fix is wider
  than PG-108's own scope. Report it before continuing rather than folding it in silently.
- **Risk: a broad keyword imports a lot of mail** (§D22.6). Worth a hand-check on the real vault
  with a deliberately narrow keyword before trusting it on «Re».
- **Risk: `MailMessageRow` is in `sharedSources`.** A field added there is compiled into both
  command-line targets. It is a plain `[String]` with no import, so this is a build-check, not a
  design risk — but build both schemes (Task 6.2) rather than assuming.
- **Risk: the `.sheet(item:)` re-render trap** (§D21.4) fails silently as a spinner that never
  resolves. It is called out in Task 5's notes because it will not show up as a test failure.
- **Not a risk, worth stating: no schema migration anywhere.** `PraticaLedger.PraticaState.entries`
  already exists and already decodes with `decodeIfPresent`; a ledger written before this work
  loads unchanged and fills its bridge on the next sync.
